# 技术笔记

记录逆向过程中的结论、试过但失败的方案、以及踩过的坑。目的只有一个：**别让后来的人重复踩**。

## 1. 原版协议是怎么确定的

不是猜的，是在 wine 里把原版 32 位 `xToolsEx.dll` 加载起来、挂一个探针程序观察它到底做了什么：

- handler 键名 `xToolsExtension`，CLSID `{B0AA8F05-5A43-411D-8D41-09C3299F0B60}`
- 只挂 `HKCR\*\shellex\ContextMenuHandlers` 与 `HKCR\Directory\shellex\ContextMenuHandlers`
- 一次 `QueryContextMenu` 插入 **3** 个菜单项
- 点击后的实际动作：`%TEMP%\~XTLS50.tmp` 被重写（CRLF、每行一个完整路径、ANSI/CP_ACP），
  随后命令行是 `"...\xTools.exe" -a`

原程序读完后是否删除该文件：未确认（只确认会被重写）。所以策略是「启动成功就不管它，启动失败就自己删」。

## 2. 试过但无效的投递方式（不要再试）

| 方式 | 结果 |
|---|---|
| 命令行直接传路径 | 主程序 listview 的 `LVM_GETITEMCOUNT` 仍是 0 |
| `WM_COPYDATA`（多种格式） | 主程序 WndProc 一律返回 0 |
| `WM_DROPFILES` | 主程序没有 `WS_EX_ACCEPTFILES`，它走的是 OLE `RegisterDragDrop`（导入表可证），消息投递无效 |
| OLE 拖放（直接调它的 `IDropTarget`） | **让 Explorer 崩溃**，原因见下节 |

### OLE 拖放为什么必然崩

OLE 在 `RegisterDragDrop` 时把拖放目标存进窗口属性 `OleDropTargetInterface`。
但 `xTools.exe` 是**独立进程**——那个属性里存的是**它自己进程地址空间里的指针**。
在 Explorer 进程里 `GetPropW` 读到的只是同一个数值，指向的是另一个进程的内存，在进程里完全无效。
强转成 `IDropTarget*` 再调虚方法 = 访问非法地址。

窗口属性不是跨进程共享机制；OLE 内部靠 marshal 处理跨进程拖放，**没有公开 API 能取得可用的
`IDropTarget`**。所以这条路在架构上不成立，不是参数调错的问题，调坐标、换键状态都没用。

## 3. 写了哪些注册表位置，为什么

`g_regTargets` 五个 base：

```
*                       右键任意文件
Directory               右键文件夹（图标态）
Folder                  右键文件夹（通用）
Drive                   右键驱动器
Directory\Background    右键文件夹内的空白处
```

`Folder` 与 `Directory` 有重叠，部分系统上会因此多插一项；如果只想显示一次，摘掉 `Folder` 即可。

**为什么写 `HKLM` 而不是 `HKCU`**：Everything、Directory Opus 这类第三方文件管理器只读机器级注册，
只写 `HKCU\Software\Classes` 它们在菜单里看不到。代价是安装必须提权。

**四个视图要一起处理**：`KEY_WOW64_64KEY` 与 `KEY_WOW64_32KEY` 各一套（对应 64 位/32 位宿主）。
不要手拼 `Wow6432Node` 路径——那个字符串是给 32 位程序看的，64 位进程直接拼会写错位置。

## 4. 回滚策略：备份值，不删整套

注册中途失败要回滚，但「失败就把整套注册删掉」是破坏性做法——那会连带删掉用户原本就有的东西
（比如同一个 CLSID 上别的扩展写的值）。

现在的做法：**注册前先把每个要写的位置备份下来**（键是否存在、值是否存在、类型、原始字节），
失败时只恢复**实际尝试写过的**那些项。

两个关键细节：

- 回滚用 `RegOpenKeyExW` 打开，**不用 `RegCreateKeyExW`**。后者会凭空创建整条路径，
  回滚反而在注册表里造出新东西。
- 删键要等**同一个键的所有备份值都恢复完**再做。`RegDeleteKey` 只要求没有**子键**，
  它根本不看键里还有没有值——所以按值逐个删键，会把键提前删掉，后面的值就无处可写。

已经明确不做的一件事：清理「注册过程中新建的父级空键」（如 `...\shellex\ContextMenuHandlers`）。
空 handler 键对 Shell 无害，而要安全清理它必须逐级记录每层原本是否存在，
不能盲删整条链（会把别人挂在同一层的扩展一起带走）。收益和风险不成比例。

## 5. 图标：只有一张 24bpp 的 32×32

`xTools.exe`（PE32，381,952 B）的 `RT_GROUP_ICON` 只有 **1 项**：32×32、24bpp、3240 B。
没有 16×16，没有 256×256 PNG。

于是有两个坑：

1. 只请求 small 图标时，部分系统上 `phiconSmall` 返回 NULL → 菜单项没图标；
2. 老式 24bpp 无 alpha 的图标走 `DrawIconEx` 到 32bpp DIB 时，某些 GDI 实现会把 alpha 全写 0，
   预乘后整张变全透明 → 看着像没图标。

现在的处理：大/小图标都取（`hSmall ? hSmall : hLarge`），并在转换时检测 alpha 全 0，
用 `DI_MASK` 重建透明度（遮罩里白=透明、黑=不透明）。

## 6. 脚本的编码坑（很隐蔽）

- **PowerShell 5.1 读无 BOM 的 UTF-8 会按 GBK 解码**，中文会把后面的闭合引号一起吞掉，
  于是报一堆看不懂的语法错误（`MissingCatchOrFinally`、乱码如 `宸茬Щ闄ゆ棫娉ㄥ唽`）。
  对策：`.ps1` 全文件纯 ASCII + BOM + CRLF，需要的中文用 Unicode 码位拼出来。
- **`*` 是合法注册表键名，但 `Test-Path` / `Get-ChildItem` 把它当通配符**，
  于是去枚举 `Software\Classes` 下几万个键，PowerShell 直接满载 CPU。
  对策：全部改用 `reg.exe` 或 `-LiteralPath`。

## 7. 编译坑

| 坑 | 说明 |
|---|---|
| `vector::emplace_back` | C++11 返回 `void`，想拿引用是 C++17 的行为 |
| `IDataObject::DAdvise` | 第二个参数是 `DWORD`，不是 `ADVF`（枚举会被当作类型不匹配） |
| `SHCreateStdEnumFmtEtc` | 不是全大写 `SHCreateStdEnumFMTETC` |
| `-fno-exceptions` | 源码有 `try/catch`，加了编不过；异常必须能越过回调边界才有意义 |
| `std::to_wstring` | 会把 libstdc++ 的数字格式化整套拉进来，白涨约 50 KB |
| 依赖数量 | 恒为 7 个；多一个就可能在某些机器上加载失败、菜单静默消失 |

## 8. 投递时序与并发

固定文件名 `~XTLS50.tmp` 无法并存，所以用命名互斥量 `Local\xToolsEx64_Handoff`
把「写列表 → 启动 → 等窗口」串行化。

两个容易被忽略的点：

- **锁内等窗口，锁外置前**。等窗口最多 5 秒，不能把置前也放进去，否则连续右键会互相阻塞。
- **失败时必须在锁内删掉临时文件**。如果留给析构去删，那时锁早就放开了，
  下一次投递可能已经写好同名文件，会被这次误删——第二次启动的主程序就读不到列表。

删除失败时的策略：锁内有限重试（4 次 × 20ms，覆盖杀软/索引器的瞬态占用），
之后无论如何放弃。残留一个 tmp 无害：下次投递用 `CREATE_ALWAYS` 直接覆盖它。

`~XTLS50.tmp` 万一是**文件夹**，`CreateFileW(CREATE_ALWAYS)` 必然失败，
所以投递前先检查：是目录就改名让位（`.bak` / `.bak2` …，同卷 rename 不复制内容），
只读文件则清掉只读位；清不掉就直接报错，把完整路径告诉用户。
